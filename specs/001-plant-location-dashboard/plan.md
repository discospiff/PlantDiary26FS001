# Implementation Plan: Plant Location Dashboard

**Branch**: `001-plant-location-dashboard` | **Date**: 2026-11-24 | **Spec**: [spec.md](spec.md)

**Input**: Feature specification from `/specs/001-plant-location-dashboard/spec.md`

## Summary

Extend the existing .NET 10 ASP.NET Core Razor Pages application with a single home-page
experience that retrieves the two public plant feeds, joins specimens to frequently watered
plants, and displays every valid match in deterministic order. The design keeps feed retrieval
and composition server-side, uses typed models and built-in JSON support, and treats either feed
failure as a complete error state. The application will run locally through Visual Studio 2026
and deploy to Azure App Service through a protected GitHub Actions workflow.

## Technical Context

**Language/Version**: C# with .NET 10 and nullable reference types enabled

**Primary Dependencies**: ASP.NET Core Razor Pages, `HttpClientFactory`, `System.Text.Json`,
Bootstrap assets already present in the project

**Storage**: None; the feature is read-only and has no application database

**Testing**: xUnit-based .NET unit and integration tests; HTTP integration tests use
deterministic in-memory responses

**Target Platform**: Local Visual Studio 2026 development and Azure App Service

**Project Type**: Single server-rendered web application

**Performance Goals**: At least 95% of normal page visits show combined results or a clear empty
state within 3 seconds; avoid repeated feed requests within a short-lived request/cache window

**Constraints**: Both feeds are required for combined results; no search, filtering, pagination,
or interactive map; no credentials in source control; use accessible loading, error, empty, and
success states

**Scale/Scope**: One public page, two public read-only feeds, one application project, one test
project, and one GitHub Actions deployment workflow
